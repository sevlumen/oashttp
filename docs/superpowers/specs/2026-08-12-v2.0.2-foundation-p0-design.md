# v2.0.2 Foundation P0 Design

## Goal

Harden the existing typed `net/http` + OpenAPI foundation by removing semantic drift between request validation and generated schemas, and by centralizing HTTP response-body status semantics. This is a correctness release, not a feature expansion.

## Scope

This design covers two P0 areas:

1. shared validation-rule semantics used by runtime validation and schema/OpenAPI generation;
2. shared HTTP response-body status semantics used by runtime response writing and operation/OpenAPI validation.

Out of scope:

- CORS, OAuth/OIDC, request IDs, rate limiting, logging, metrics, or other new application features;
- public API redesign;
- deterministic OpenAPI component naming;
- broader schema-reflector cleanup unrelated to validation parity;
- third-party runtime dependencies.

## Compatibility

- Keep the public `github.com/sevlumen/oashttp/v2` API source-compatible.
- Keep Go 1.22 as the minimum supported Go version.
- Keep zero third-party runtime dependencies.
- Preserve existing runtime behavior except where the current behavior or generated schema is incorrect.
- Preserve existing OpenAPI output for unaffected operations.
- Release the completed fixes as patch version `v2.0.2` after final verification.

## Problem 1: duplicated validation semantics

Today runtime validation and schema generation interpret `validate` tags independently:

- `internal/validation` parses tags into executable runtime rules;
- `internal/schema` parses the same tags again to emit OpenAPI/JSON Schema keywords.

The duplicated interpretation already produces observable drift. Examples:

- runtime `min`, `max`, and `len` on maps operate on `len(map)`, but schema generation currently emits array keywords instead of object-property keywords;
- runtime numeric `oneof` compares numeric values by their textual form, while schema generation currently emits string enum values even when the field schema is numeric.

The root cause is two independent parsers with no shared normalized representation.

## Design: shared validation-rule IR

Introduce a dependency-light internal package, tentatively `internal/validationrule`, that owns only validation tag syntax and normalized rule semantics.

It must not:

- execute validation against request values;
- import OpenAPI model types;
- import binding, operation, or the public `oashttp` package;
- contain HTTP-specific behavior.

It will expose an internal normalized representation sufficient for both consumers. Conceptually:

```go
type Kind uint8

const (
    Required Kind = iota
    Min
    Max
    Len
    Email
    UUID
    E164
    OneOf
    GTE
    LTE
)

type Rule struct {
    Kind    Kind
    Integer int
    Number  float64
    Choices []string
}

func Parse(t reflect.Type, tag string) ([]Rule, error)
```

Exact identifiers may differ during implementation, but the ownership boundary must remain the same.

### Runtime validation consumer

`internal/validation` will consume the normalized rules and keep responsibility for:

- traversing structs;
- reading field values;
- nil/zero handling;
- measuring strings, collections, and numbers;
- rendering validation messages;
- producing `core.FieldError` values.

It will no longer independently parse validation tag syntax.

### Schema consumer

`internal/schema` will consume the same normalized rules and translate them into schema constraints. It will no longer independently parse supported validation tags.

Mapping requirements:

- string `min` / `max` / `len` → `minLength` / `maxLength`;
- slice/array `min` / `max` / `len` → `minItems` / `maxItems`;
- map `min` / `max` / `len` → `minProperties` / `maxProperties`;
- numeric `min` / `max` → numeric `minimum` / `maximum`, preserving current runtime meaning;
- `gte` / `lte` → `minimum` / `maximum`;
- `email` → `format: email`;
- `uuid` → `format: uuid`;
- `oneof` → schema `enum` values converted to the field's scalar type rather than always emitted as strings;
- `required` continues to influence object required-property lists rather than adding a field-local keyword.

If a normalized rule cannot be represented safely for the target field type, build/schema generation must fail rather than silently emit an incorrect schema.

### `oneof` type conversion

For schema generation, `oneof` choices must be converted using field type semantics:

- string-like fields → strings;
- booleans → booleans;
- signed integers → signed integer values;
- unsigned integers → unsigned integer values;
- floats → numeric values.

Pointer types use their element type for conversion. Unsupported `oneof` target kinds fail at build time.

Runtime validation behavior remains compatible: choice matching must continue to accept the same values that were valid before this change.

## Problem 2: duplicated HTTP response-body status rules

Runtime response writing and operation/OpenAPI validation currently maintain separate status checks. They agree on common cases but do not fully encode HTTP semantics. In particular, `205 Reset Content` must not carry response content.

Duplicated status logic creates a risk that runtime and generated API documentation diverge.

## Design: shared HTTP status semantics

Introduce one small internal helper owned by a dependency-light package appropriate for HTTP protocol facts. The helper will answer whether a response status permits a message body/content representation.

Required behavior:

- all informational `1xx` statuses: no response body;
- `204 No Content`: no response body;
- `205 Reset Content`: no response body;
- `304 Not Modified`: no response body;
- ordinary successful/error statuses such as `200`, `201`, `400`, `500`: body allowed.

Both runtime result writing and operation/OpenAPI response validation must use the same helper.

The helper must not depend on operation, schema, or public facade packages.

## Error handling

Validation tag syntax remains a build-time contract. Unknown rules, missing arguments, invalid numeric arguments, incompatible field kinds, or impossible typed `oneof` conversion must return deterministic errors during compilation/build.

No new request-time error class is introduced by this work.

For response statuses that do not permit bodies, runtime must not serialize or write a body, and generated OpenAPI responses must not describe response content for those statuses.

## Testing strategy

Implementation must follow RED → GREEN TDD.

### Validation/schema parity tests

Add focused tests covering the same field definitions through both runtime validation and schema generation:

- string `min`, `max`, `len`;
- slice/array `min`, `max`, `len`;
- map `min`, `max`, `len` with `minProperties`/`maxProperties`;
- signed integer `oneof`;
- unsigned integer `oneof`;
- float `oneof`;
- boolean `oneof` if supported by the existing validation contract;
- string `oneof`;
- `gte` / `lte`;
- incompatible rules and malformed arguments.

Tests must demonstrate the existing incorrect map/typed-enum behavior before the production fix.

### HTTP status matrix tests

Add a shared table covering at least:

- `100`, `101`, `199` → no body;
- `200`, `201` → body allowed;
- `204` → no body;
- `205` → no body;
- `304` → no body;
- `400`, `500` → body allowed.

Test both runtime result writing and generated/compiled response behavior so the shared rule is observable from both paths.

### Regression and release gates

Final head must pass:

- Go 1.22, 1.23, 1.24, 1.25, and 1.26 matrix;
- formatting;
- zero runtime dependency check;
- module consistency;
- `go vet ./...`;
- repeated shuffled tests;
- `go test -race ./...`;
- coverage floor >= 70%;
- OpenAPI golden verification;
- route fuzz target;
- binding fuzz target;
- benchmarks;
- `govulncheck ./...`.

## Release completion

After implementation review and green CI:

1. update `Version` to `2.0.2`;
2. update README installation/version references where applicable;
3. add a `2.0.2` changelog entry describing only the correctness/foundation changes actually shipped;
4. merge the reviewed PR into `main`;
5. require a green push-triggered CI run on the exact final `main` commit;
6. publish `v2.0.2` through the existing guarded `publish/v2.0.2` release workflow;
7. verify the tag and GitHub Release point to the exact verified `main` commit.

## Definition of Done

This P0 is complete only when:

- runtime validation and schema generation share one validation-rule parser/IR;
- map length rules emit object-property constraints;
- typed `oneof` emits type-correct enum values;
- runtime and OpenAPI use one HTTP body-status rule including correct `205` behavior;
- no public API or runtime dependency is added;
- final `main` CI is green;
- public Git tag and GitHub Release `v2.0.2` are published from the verified final `main` commit.
