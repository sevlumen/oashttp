# v2.0.1 P0-P1 Design

## Goal

Ship an additive, backward-compatible v2.0.1 candidate that fixes the v2 security-support policy and adds the production integration boundaries identified during review: raw `http.Handler` operations, scoped middleware, operation metadata in context, and a generic named security-provider foundation.

## Compatibility

- Existing typed `MapGet`/`MapPost`/`MapPut`/`MapPatch`/`MapDelete` behavior remains unchanged.
- Existing `Config.Authenticator`, `Config.Authorizer`, and `RequireFeatureAndPermission` remain supported.
- Existing default `bearerAuth` OpenAPI output remains unchanged for legacy protected operations.
- No new third-party runtime dependencies.

## Raw handlers

Add `MapHandler(group, method, path, http.Handler)` returning a `RawOperationBuilder`. Raw operations share route parsing, duplicate-route detection, OpenAPI registration, security, operation metadata, scoped middleware, and panic recovery with typed operations. They intentionally skip typed binding and validation. Response documentation remains explicit through `Produces`, `ProducesProblem`, and `ProducesResponse`.

## Scoped middleware

`Group.Use` applies middleware to subsequently registered operations in that group. Nested groups inherit the parent middleware snapshot at group creation. `OperationBuilder.Use` and `RawOperationBuilder.Use` add per-operation middleware.

Execution order for an operation is:

1. outer panic recovery;
2. application middleware (`App.Use`);
3. operation metadata injection;
4. authentication/authorization;
5. group middleware, outer to inner;
6. operation middleware;
7. typed binding/validation or raw handler.

Scoped middleware therefore sees both operation metadata and an authenticated `Principal` when security is enabled.

## Operation metadata

Expose `OperationInfo`, `OperationFromContext`, `OperationID`, and `RoutePattern`. Metadata is attached before authentication so security and scoped middleware can consume it.

## Security provider foundation

Add public `SecurityScheme` and `SecurityProvider` abstractions and `Config.SecurityProviders map[string]SecurityProvider`. Add `RequireSecurity(name)` to typed and raw builders.

A security provider authenticates directly from `*http.Request`, so schemes are not coupled to the `Authorization` header. OpenAPI security schemes come from the provider's declared scheme. Legacy `Config.Authenticator` is adapted internally to the existing RFC 6750 bearer behavior under `bearerAuth`.

Authorization remains feature/permission based in v2.0.1. OAuth2 flow objects and scope authorization are deferred to P2 so the patch release does not pretend to support semantics it cannot enforce.

## Security policy

`SECURITY.md` will state that v2.x is fully supported and v1.x receives security fixes only. No unsupported end-of-life date is invented.

## Tests

Add regression tests for raw routing/OpenAPI, middleware ordering/inheritance, operation context metadata, named providers, legacy bearer compatibility, duplicate routes, freeze behavior, and the security policy documentation. Existing race, fuzz, coverage, benchmark, vet, and govulncheck CI remain authoritative release gates.
