# v2.0.1 P0-P1 Design

## Goal

Ship an additive, backward-compatible v2.0.1 candidate that fixes the v2 security-support policy and adds the production integration boundaries identified during review: raw `http.Handler` operations, scoped middleware, request-scoped operation/principal metadata, and a generic named security-provider foundation.

## Compatibility

- Existing typed `MapGet`/`MapPost`/`MapPut`/`MapPatch`/`MapDelete` behavior remains unchanged.
- Existing `Config.Authenticator`, `Config.Authorizer`, and `RequireFeatureAndPermission` remain supported.
- Existing default `bearerAuth` OpenAPI output and RFC 6750 behavior remain unchanged for legacy protected operations.
- Existing `App.Use` middleware remains application-wide.
- No new third-party runtime dependencies.
- The module version remains `2.0.0` until the release review is approved; this branch records changes under `Unreleased`.

## Raw handlers

Add `MapHandler(group, method, path, http.Handler)` returning a `RawOperationBuilder`. Raw operations share route parsing, duplicate-route detection, OpenAPI registration, security, operation metadata, scoped middleware, and panic recovery with typed operations. They intentionally skip typed JSON binding and validation.

Raw route constraints such as `{id:uuid}` are still enforced before the user handler runs. This prevents the raw escape hatch from changing route constraints into documentation-only metadata.

Response documentation remains explicit through `Produces`, `ProducesProblem`, and `ProducesResponse`. `Consumes(contentTypes...)` documents raw request media types in OpenAPI without parsing or buffering the body. The user handler remains responsible for `Content-Type` enforcement, body-size limits, multipart rules, and streaming behavior.

## Scoped middleware

`Group.Use` applies middleware to subsequently registered operations in that group. Nested groups inherit the parent middleware snapshot at group creation. `OperationBuilder.Use` and `RawOperationBuilder.Use` add per-operation middleware.

Execution order for a routed operation is:

1. request-state carrier;
2. panic recovery when enabled;
3. application middleware (`App.Use`);
4. routing and operation metadata selection;
5. authentication/authorization;
6. group middleware, parent to child;
7. operation middleware;
8. typed binding/validation or raw path-constraint validation;
9. handler.

Scoped middleware therefore sees both operation metadata and an authenticated `Principal` before the handler.

## Request-scoped metadata

Expose `OperationInfo`, `OperationFromContext`, `OperationID`, and `RoutePattern`. Metadata is recorded before authentication so security and scoped middleware can consume it.

A race-safe request carrier is installed outside recovery and application middleware. Routing records `OperationInfo` and authentication records `Principal` into that carrier. This gives three useful visibility points without changing the public context API:

- scoped middleware and handlers see operation/principal data before execution;
- application-wide middleware can read populated data after `next.ServeHTTP` returns;
- `Config.ErrorHandler` can read operation metadata when reporting a recovered panic from a routed operation.

## Security provider foundation

Add public `SecurityScheme` and `SecurityProvider` abstractions and `Config.SecurityProviders map[string]SecurityProvider`. Add `RequireSecurity(name)` to typed and raw builders.

A security provider authenticates directly from `*http.Request`, so schemes are not coupled to the `Authorization` header. OpenAPI security schemes come from the provider's declared scheme. The patch supports the OpenAPI fields required by `type: http` and `type: apiKey` providers.

The name `bearerAuth` remains reserved for the legacy `Config.Authenticator` integration so named providers cannot silently overwrite its OpenAPI component.

Authorization remains feature/permission based in v2.0.1. OAuth2/OpenID Connect flow objects and first-class scope authorization are deferred to P2 so the patch release does not pretend to support semantics it cannot enforce.

## Security and support policy

`SECURITY.md` states that v2.x is fully supported and v1.x receives security fixes only. `SUPPORT.md` applies the compatibility promise to major version 2 and identifies `MapHandler` as the supported escape hatch for streaming/custom representations. No unsupported end-of-life date is invented.

## Tests

Regression coverage includes:

- raw routing, OpenAPI registration, request media types, and runtime route constraints;
- middleware ordering, inheritance, freeze behavior, and duplicate routes;
- operation metadata in handlers, scoped middleware, global middleware, and panic reporting;
- principal visibility in scoped and global middleware;
- named providers and generated OpenAPI security schemes;
- legacy bearer compatibility;
- v2/v1 security and support policy documentation.

Existing race, fuzz, coverage, benchmark, vet, golden-OpenAPI, and `govulncheck` CI remain authoritative release gates.
